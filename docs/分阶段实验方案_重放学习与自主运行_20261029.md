# 分阶段实验方案：专家重放学习与自主运行后的 Harness 优化

日期：2026-10-29  
工作仓库：`spike-sorting-agent-tianmin`  
状态：实验设计记录；用户表示 baseline 已在运行，本文未独立核验其运行状态或结果。本次只记录方案，不修改运行中的代码、不启动新实验。文中区分用户确定的方向与建议补充的评估约束。

## 1. 实验要回答什么

用户提出的顺序是：先跑 baseline 并观察响应时间；再用 CH3、CH31 的反馈更新判断层，在 CH20、CH30 上测试步骤准确率；随后让更新后的 agent 自主处理整个 dataset；完整运行结束后，结合结果和 trace 更新控制流，再重新评估。

这一顺序合理，因为它依次回答三个不同的问题：

1. 固定题目和状态时，反馈学习能否改善模型的判断？
2. 把改善后的判断能力放进现有 controller，能否改善完整任务结果？
3. 判断层保持不变时，控制流优化能否进一步改善结果或减少成本？

“当前 skill 可能很强”是待验证的观察，不是削弱 baseline 的依据。保留正在运行的真实基线，结果出来后再判断是否存在准确率天花板、类别不均衡或历史开发曝光。

## 2. 两种运行方式

### 2.1 严格专家重放：题目和状态由专家记录决定

在专家第 t 步操作之前恢复对应状态，直接取出专家处理的簇或簇对，向模型提问。先保存模型答案，再揭示专家答案并计分。无论模型答对与否，都执行专家动作，进入下一步。

模型不负责决定下一道题，因此不存在 controller 漏选专家合并对象的问题。更新前后可以在完全相同的状态、对象和观测上配对比较。重放终态由专家动作决定，不能作为模型独立完成任务的成绩。

当前本地已存在 `scripts/run/run_expert_replay.py`。它与 `run_local_rollout.py --simulated-expert` 的含义不同，后者仍由 controller 选题。实验产物应记录实际入口，而不是仅写“teacher forcing”。

当前重放入口还支持补充推导的 KEEP 题目，并处理撤销记录。正式统计前需要冻结题目清单及规则：真实编辑、推导 KEEP、不可评分或撤销步骤分别计数。基线和更新版本使用相同规则、相同题目，不把推导标签表述为人类实际记录。`--keep-before-merge` 等会改变题目构成的设置也必须固定。

### 2.2 自主运行：题目和状态由 agent 自己决定

这里“直接跑”指：从与基线一致的初始分群、层级树和 spike 数据开始，由 controller 选择要检查的簇、候选合并对象、复核顺序和停止时机；模型作出判断，执行器实际修改分群，后续问题依赖这些修改后的状态。

运行中不注入专家动作，不依据专家记录替 agent 选题或纠正状态。专家答案和终态标签只由运行外的评估器读取。它不是重新从原始电压完成全部 spike detection，而是当前仓库定义的 curation 任务入口。

本阶段为隔离变量，每次自主运行同时冻结 skill 和 controller。学习产生的版本只在后续另一次完整运行中加载。

## 3. 数据角色和版本

| 数据 | 本轮角色 | 允许用途 |
|---|---|---|
| CH3、CH31 | 学习与开发数据池 | 重放反馈学习、候选选择、完整自主运行诊断、控制流优化 |
| CH20、CH30 | 本轮保留评估通道 | 冻结版本后的重放评估和自主运行评估；不将其错误、trace 或评分送入优化器 |

CH3 与 CH31 来自同一路径推定录音块，不能当作两个完全独立的录音样本。四个通道均已有历史开发曝光，因此 CH20、CH30 是“本轮保留评估通道”，不是从未曝光的最终测试集。严格泛化结论需要新增未参与开发的录音。

候选选择也消耗开发数据。ACE 的反馈输入与 GEPA 的候选选择数据应在 CH3、CH31 内提前分配并冻结；优先按通道或连续轨迹段划分，记录状态关联，避免随机打散相邻步骤造成虚假的独立性。即使分开，它们仍可能相关，不能把内部选择分数当作跨录音泛化成绩。具体划分在学习运行前确定，不能借用 CH20、CH30 选候选。

定义三个版本符号，避免把“更新”混为一谈：

- **S0**：当前 baseline 使用的 skill，按实际内容和哈希固定。
- **S1**：仅使用开发数据反馈，经 ACE＋GEPA 接受的 skill；若没有候选通过验收，S1 可以等于 S0。
- **H0 / H1**：当前 controller 与完整自主运行后选出的 controller 候选。H1 尚待实现和验证。

这些符号不是仓库的 `skill_v1`、`skill_v4` 文件名；每次运行都应保存实际路径和哈希。不同执行模型分别维护 S0/S1、学习 session 和优化历史，不默认共享学习成果。

## 4. 阶段 A：完成 baseline，建立准确率与时间参照

保持正在运行的 baseline 设置不变，完整保存四个通道的结果和配置。先确认它采用严格专家重放、未开启学习，再作为本方案的步骤基线。

主要报告每通道正确数 / 有效题目数及步骤 accuracy，同时分别报告真实编辑题和推导题、各动作类别的结果。总体同时给出按题目数加权的 accuracy 与各通道 accuracy 的平均值，避免大通道掩盖小通道。

响应时间至少区分：观测与图片准备时间、每次模型请求耗时、整个 dataset 的墙钟时间。模型请求报告中位数、P90 和样本数；并行时不能把请求耗时之和当作实际等待时间。记录模型端点、thinking 设置、token 数、并发数、预取设置、超时与失败次数；冷启动或预热条件另作说明。未记录首 token 时间时，不把完整请求耗时叫作首 token 延迟。

保留未完成和格式错误的统计。不能仅删除失败请求后报告成功请求上的高 accuracy；如同时报告有效回答准确率，应另报覆盖率及以全部计划题目为分母的正确完成率。

如果强 skill 已接近满分，先检查按类别表现、简单固定策略参照和题目构成。若仍存在天花板，可预先定义一个较简 skill 的独立消融分支，并为它重新建立完整对照；不能看完测试错误后定向删除规则，再把较弱版本替换成主 baseline。

## 5. 阶段 B：重放学习判断层，再跨通道评估

在 CH3、CH31 的开发数据上，采用已经确定的 ACE＋GEPA 方法：累计 N 条有效反馈，ACE 式反思整理经验，冻结建议，GEPA 搜索 skill 候选，经过内部验证后接受或拒绝。N、反馈来源、只收错误还是收全部反馈、搜索预算和通道顺序均在运行前确定。

每个题目必须先预测、再揭示反馈。同一批并行问题使用同一 skill，批次结束才更新，不能用当前题答案先优化再给当前题计入“更新后准确率”。学习过程中的曲线反映在线适应，不等于保留通道上的泛化结果。

学习完成并选定 S1 后，冻结全部经验、skill 和优化器状态，在 CH20、CH30 上关闭学习，重放与 baseline 完全相同的问题，比较 S0 与 S1：

- 总体、分通道、分动作和分来源的 accuracy。
- 同一题从错变对、从对变错的数量，尤其是误删、误合并的回归。
- 请求延迟、token 和执行成本；优化额外消耗的调用、时间和费用单列。

S1 只能由开发数据选出。若同时试验多个 N、不同 skill 起点或多个学习方案，不得根据 CH20、CH30 的结果反复挑赢家后仍声称它们是独立测试。若这些结果被用于改设计，应将该轮明确降格为开发性探索，并准备新的评估数据。

## 6. 阶段 C：冻结 S1，以 H0 自主运行完整 dataset

先在 CH3、CH31 上运行 S1＋H0，收集完整结果与 trace，用于下一阶段的 controller 诊断。每个 dataset 从原始初始状态开始，运行中固定 S1、H0，不进行专家强制执行，也不进行在线 skill 学习。

这里“看完一轮”以完整 dataset 的自主运行结束为最小单位，随后可以触发一次 harness 优化会话。也可配置为收齐 CH3、CH31 后统一触发；这是触发频率选择，不限制优化 agent 自主决定修改位置。它不指 controller 内部的一个 round，也不指累计 N 条反馈。

异常或达到预算上限的运行保留停止状态和 trace，可以用于排错，但不能标成完整成功运行。主表同时报告完成率，完整终态与停止状态分开统计。

为了判断 skill 的重放收益是否迁移到自主运行，用户已确认补跑 S0＋H0 的自主运行对照，与 S1＋H0 比较。

## 7. 阶段 D：根据完整开发轨迹优化控制流

本阶段采用开放式自主 harness 优化方向：优化 agent 在完整开发运行结束后，自主阅读代码、结果与 trace，调查问题并实现新代码候选。以 Meta-Harness 式自主编程循环为主要架构参考，具体设计见 [自主 Harness 优化方案](自主Harness优化_设计方案_20261029.md)。本段覆盖此前“只开放几个预设策略”的建议，不表示该能力已经实现。

固定执行模型与 S1，允许优化 agent 自主选择 harness 的修改位置、跨函数修改或重构工作流；不预先把搜索限制为 top-k、排序等策略选项。任务定义、数据入口、评分器、预算执行和测试隔离保持固定。如果候选改变观测、额外上下文或模型调用组织，收益应归于整体 harness，而不能只归于狭义调度。

从 trace 中区分：模型在已问问题上判断错误、controller 没有提出必要问题、正确动作因冲突未执行，以及过早停止或重复处理。终态差异本身不能证明原因，候选应有可核查的状态和事件证据。

建议的内部实现流程是：

1. 汇总 CH3、CH31 完整运行的状态、候选列表、排序依据、模型答案、实际操作与评分。
2. 由优化 agent 自主调查并提出带证据的修改假设，不写入通道名、簇 ID 或专家答案捷径。
3. 由优化 agent 实现独立的可执行 H 候选，在固定预算下检查接口、动作合法性、状态一致性和停止行为。
4. 用同一个 S1，从相同初始状态完整重跑开发数据，比较 H0 与候选。
5. 按预先确定的质量、误删/误合并和成本标准选出 H1；无合格候选时保留 H0。

冻结题目的 replay 无法评估选题策略变化。controller 候选的主要验收必须执行完整自主运行；固定 replay 只能补充检查判断接口是否发生意外变化。若以后复用 GEPA 搜索，需要先将这些完整运行结果接入其候选评估，而不是沿用现有步骤回放评分器。

执行 trace 应区分“模型答案”“提交动作”“实际执行”“因冲突作废”，并记录未执行原因。不能将提交给执行器的 MERGE 次数直接当作实际 MERGE 次数。

## 8. 阶段 E：冻结 H1 后，在保留通道上评估

在 CH20、CH30 上分别运行 S1＋H0 和 S1＋H1，使用相同初始数据、执行模型、预算和停止约束；不能从 H0 的终态继续执行 H1。H1 的选择不读取这两个通道的 trace 或终态结果。H0 的保留通道运行可以提前收集，但其结果不参与 H1 的开发决策。

自主运行的主要“准确性”采用终态分群质量，例如沿用仓库既有的一对一匹配协议报告 precision、recall、F1，同时报告误删、过度合并/碎片化、完成率、调用量和运行时间。固定现有评分协议与阈值，不随结果调整。

自主运行不能把 agent 第 t 步与专家第 t 步直接比较：两者的状态、簇成员和问题可能不同。如果需要辅助步骤 accuracy，必须在 agent 实际访问的状态上重新审核，或使用严格适用的状态匹配标签，并报告可标注覆盖率。该指标与固定专家轨迹上的 accuracy 分开命名、分开汇总。

允许控制流改变题目数量，因此不能只比较“它自己选出来的题上的 accuracy”；更保守的 controller 可能少问难题，表面 accuracy 上升而终态变差。

## 9. 最小对照表

| 条件 | skill | controller | 运行方式 | 主要用途 |
|---|---|---|---|---|
| R0 | S0 | 专家记录固定选题 | 严格重放，无学习 | 当前 baseline |
| R1 | S1 | 与 R0 相同题目 | 严格重放，无学习 | 判断层更新的保留通道收益 |
| F0（已确认补跑） | S0 | H0 | 自主运行 | 判断层更新能否改善完整任务 |
| F1 | S1 | H0 | 自主运行 | 当前控制流的参照与开发轨迹 |
| F2 | S1 | H1 | 自主运行 | 控制流修改的增量收益 |

R1 与 R0 的差异检验判断层；F1 与 F0 的差异检验其自主运行迁移；F2 与 F1 的差异检验控制流。开发通道和保留评估通道分表，不混合平均。表中 R1 是学习完成后的冻结评估，不是学习过程本身。

初轮单次运行用于探索，不把小幅变化直接解释为稳定提升。后续在预算允许时用预定重复次数和相同运行条件复测，并保存每次结果。不能把同一条轨迹内相关的数十个步骤视为数十个独立 dataset。

## 10. 实验产物与实施前待定参数

每次优化保存：允许读取的数据范围、反馈 N 与来源、训练/内部选择划分、父版本、候选及修改理由、搜索预算、验收分数、接受或拒绝原因。运行和优化的耗时分别报告。

以下参数尚未由本次讨论确定，实施前应写入配置，不能把本文建议误作既定值：N、反馈来源与范围、学习顺序、内部候选选择划分、模型与推理设置、自主编程优化器和候选运行接口、候选预算、验收门槛和重复次数。
