# Dataset 完成后的自主 Harness 优化：设计方案

日期：2026-10-29  
工作仓库：`spike-sorting-agent-tianmin`  
状态：设计讨论记录，尚未实现自主 harness 代码优化。本次授权为编写文档，不启动优化、部署或模型调用。

## 1. 目标与已经确定的方向

一个开发 dataset 完整自主运行结束后，让优化 agent 阅读当前代码、运行结果和执行 trace，自主判断问题所在，并实现新的 harness 候选。独立评估程序通过完整重跑检验候选，合格版本在后续运行中生效。

用户明确不希望我们预先决定“只有哪些局部模块或参数可以优化”。因此，本方案以可执行 harness 程序作为优化对象，允许优化 agent 自主选择修改位置、跨函数修改和重构工作流，不将搜索空间限定为 top-k、排序规则或几个预设策略选项。

这一方向覆盖此前“先只开放一两个预设控制策略”的建议。我们仍固定任务定义、评估协议和实验条件；这些条件用于判断修改是否有效，不用于预先替优化 agent 选择解法。

已确定的实验关系：

- 判断层继续采用 ACE＋GEPA，累计 N 条有效反馈触发更新。
- harness 优化发生在完整 dataset 运行结束之后；运行中不更换当前 harness。
- harness 对照阶段固定执行模型和已学习的 skill，单独研究程序组织方式的收益。
- 用户已确认补跑“原 skill＋原 harness”的自主运行对照。
- CH3、CH31 用于学习与开发；CH20、CH30 是本轮保留评估通道，不进入候选生成与选择。

## 2. Tianmin 提供的参考及其作用

### 2.1 Meta-Harness：主要架构参考

Meta-Harness 搜索固定基础模型外围的可执行代码。其领域适配说明要求优化 agent 能读取既往候选、分数与完整执行轨迹，并将最终测试数据及结果隔离。[领域适配说明](https://github.com/stanford-iris-lab/meta-harness/blob/main/ONBOARDING.md)

Terminal-Bench 示例让编程 agent 生成新的 Python harness，支持重写主循环、工具、模型调用和观测处理。外层程序负责候选加载检查、运行检查、评估和历史记录。候选采用独立文件并满足固定接口，原实现和评估程序不由候选任意改写。[候选生成规则](https://github.com/stanford-iris-lab/meta-harness/blob/main/reference_examples/terminal_bench_2/.claude/skills/meta-harness-terminal-bench-2/SKILL.md)、[外层循环代码](https://github.com/stanford-iris-lab/meta-harness/blob/main/reference_examples/terminal_bench_2/meta_harness.py)

我们借鉴其“自主调查、编写候选、独立评估”的结构。它是方法参考，不意味着照搬其 benchmark、模型、预算、每轮候选数量或原库全部实现。

### 2.2 AFlow：工作流结构也可以成为修改对象

AFlow 的优化代码读取既往工作流、分数、经验和日志，生成新的 graph 与 prompt，再执行评估。其提示词允许增删节点及修改循环、分支，但当前实现也包含每次只改一个细节、限制修改行数等约束。它支持结构搜索，并非完全无约束的程序演化。[优化器](https://github.com/FoundationAgents/AFlow/blob/main/scripts/optimizer.py)、[优化提示词](https://github.com/FoundationAgents/AFlow/blob/main/scripts/prompts/optimize_prompt.py)

我们借鉴“工作流结构可以变化”，不要求把当前 spike curation 系统重写成 AFlow 的算子图，也不预设其修改行数限制。

### 2.3 GEPA：可选的候选搜索与选择机制

当前官方 GEPA 支持代码等文本产物，不只支持 prompt。适配器负责将候选变成可执行程序、返回评分与轨迹，搜索引擎利用反馈进行候选改进和选择。[官方说明](https://github.com/gepa-ai/gepa)、[适配接口](https://github.com/gepa-ai/gepa/blob/main/src/gepa/core/adapter.py)

若采用 GEPA 管理 harness 候选，需要新建完整 dataset 的执行评估器，并适配编程 agent 的候选生成过程。当前仓库固定版本的 GEPA 与现有 skill 适配器能否直接复用，应在实现前核对；不能根据最新上游接口假定本地已支持。

### 2.4 ACE：可选的优化经验积累

ACE 通过生成、反思、整理更新经验 playbook。我们可以借鉴它保存“尝试了什么、在哪些条件下有效、出现了什么副作用”，供下一次 harness 优化读取；它本身不能替代代码实现和完整运行验证。[官方说明](https://github.com/ace-agent/ace)

建议第一版以 Meta-Harness 式自主编程循环为主，保留现有判断层 ACE＋GEPA。harness 层是否正式接入 GEPA 搜索及 ACE 经验整理，属于后续实现选择，不要求同时叠加四套框架。

## 3. 一次优化会话如何工作

### 3.1 触发：完整 dataset 自主运行结束

当前 harness H0 从初始分群、层级树和 spike 数据自主运行，保存结果后触发优化会话。它不是逐步骤专家重放，也没有专家在运行中纠正状态。

一次 dataset 完成是触发点，不表示必须立即接受新版本。一个会话可以在预定预算内生成并评估多个候选。也可以配置为收齐多个开发 dataset 后统一触发；这改变触发频率，不改变自主优化机制。不同触发安排必须记录数据顺序和版本生效位置。

### 3.2 调查：自主阅读代码和运行证据

优化 agent 可以读取当前及历史 harness 源码、开发集运行结果、原始 trace、观测图像、请求与回答、状态快照和错误日志。长轨迹保留为可检索文件，不只提供一个人工总结。

它可以自主搜索日志、检查状态和编写诊断分析，决定需要进一步调查什么。预先生成的统计可以帮助检索，但不能成为唯一允许读取的证据，也不把原因限定为事先列出的错误类别。

例如，终态显示某个 unit 被分成多个碎片，它可以追查相关簇是否被比较、模型如何回答、动作是否执行、后来是否被拆回。任何因果解释都先作为假设，经过候选重跑检验。

### 3.3 实现：生成独立的可执行候选

优化 agent 选择当前或历史版本作为父版本，直接编写候选代码，并保存修改依据、预期作用及可能代价。输出不能只有自然语言建议。

允许它自主改变主循环、任务分解、信息组织、记忆维护、工具组合、模型调用安排、调度和停止逻辑。这些是开放能力的例子，不是限定可改位置的清单。候选可以包含多个文件和辅助模块，不要求局限在原 controller 的某个函数里。

父版本、差异与候选快照独立保存。代码结构、假设和实际评估结果一一绑定，避免下一轮优化覆盖上一轮结果。

### 3.4 评估：独立程序运行候选

候选先通过接口和基本可执行性检查，再在固定实验条件下从原始初始状态完整运行开发 dataset。评估程序记录质量、成本、错误和完成状态，向优化 agent 返回证据。

评估过程不能复用父版本执行后的终态作为候选起点，也不能只重放父版本选过的题目。新 harness 会改变后续状态和题目分布，必须实际执行这些变化。

### 3.5 选择：接受、继续尝试或保留旧版

候选优劣由预定评估标准决定，不由优化 agent 的自我评价决定。失败候选也保留代码、错误和 trace，供后续学习。

预算耗尽、达到预定停止条件或没有合格候选时，可以结束会话并保留原版本。被接受的版本仅在后续完整运行中启用；已完成的运行保持原版本归属。

## 4. 自主性与固定实验条件

开放的是 harness 的内部实现，固定的是任务与比较条件。

| 项目 | 本方案要求 |
|---|---|
| Harness 实现 | 优化 agent 自主选择修改位置及结构，允许重构和新增辅助逻辑 |
| 执行模型、skill | 在一次 harness 对照中固定，记录实际模型配置及 skill 内容哈希 |
| 输入与输出 | 输入为相同初始 curation 数据；输出必须能被统一评估器读取并校验 |
| 任务操作语义 | 不能通过改变分群含义、spike 身份或评分目标获取不等价的成绩 |
| 评估与预算 | 评分器、数据划分及预算执行由候选外部管理；候选不能修改或绕过 |
| 专家信息 | 开发诊断可使用许可的反馈；运行中的 agent 不可读取专家答案或终态标签 |
| 保留评估数据 | CH20、CH30 的数据、结果和 trace 不进入优化 agent 的可访问开发工作区 |

只固定 skill 文件并不等于模型接收的信息完全不变。若 harness 改变上下文组织、额外提示或复核调用，实验应称为“整体 harness 优化”。只有进一步固定观测与判断接口的独立消融，才能将收益归因于狭义的 controller 调度。

候选应在独立运行环境中执行，原始数据和评分程序保持只读，预算由外层强制执行。这里不是要求每个候选都由人手工决定修改位置；运行隔离用于保证自主生成的代码仍接受同一套评估。

## 5. 优化器应获得什么反馈

反馈同时包括结果和执行过程：

- 终态分群的 precision、recall、F1，以及误删、过度合并、碎片化等可计算诊断。
- 完成状态、停止原因、错误和超时；失败运行不能从统计中悄悄删除。
- 每次模型调用的输入、输出、时间和 token，实际执行动作及状态变化。
- 提交但未执行的操作及原因，必要的候选选择或内部决策记录。
- 历史候选的差异、评估配置和结果，包括有效与无效的尝试。

开发专家编辑记录和参考终态可能不属于同一次 curation pass，诊断时必须保留其来源区别，不能强行用不一致的参考解释同一条“正确轨迹”。

经验摘要可以作为 ACE 式记忆，内容应包含证据引用、适用条件和失败反例。摘要不替代原始 trace，也不将一次成功修改直接升级为普遍规律。

## 6. 如何评价自主修改是否有效

主评估采用完整自主运行的终态质量，同时报告完成率、调用量、耗时和费用。沿用既有一对一匹配协议与阈值，候选不能修改评分定义。

在预定预算条件下比较候选，单列增加调用所带来的收益。具体接受门槛、对个别开发通道退步的容忍度、失败计分和重复次数，在启动优化前写入评估配置；当前讨论未确定具体数值。

每完成一个 dataset 可以触发候选生成，但单个 dataset 的改善不足以证明通用改善。建议候选接受时也检查已经许可的历史开发数据，避免修复当前 dataset 后破坏之前的表现。候选数量、验证次数与累计开发曝光都应记录。

固定专家重放 accuracy 用于判断层实验。自主运行发生轨迹分叉后，不能按专家第 t 步与 agent 第 t 步直接对齐；若补充实际访问状态上的步骤审核，应另外报告标签来源和覆盖率。

## 7. 与已确定实验的衔接

| 对照 | 固定条件 | 要回答的问题 |
|---|---|---|
| 重放 S0 与 S1 | 相同专家题目与状态，测试时不学习 | 判断层更新是否改善步骤 accuracy？ |
| 自主运行 S0＋H0 与 S1＋H0 | 相同初始数据、模型与 H0 | 判断层学习是否迁移到完整任务？用户已确认补跑此项 |
| 自主运行 S1＋H0 与 S1＋H1 | 相同初始数据、模型与 S1 | 自主 harness 优化是否带来额外收益？ |

CH3、CH31 用于开发诊断与候选选择。选定 H1 后再在 CH20、CH30 比较 H0 与 H1；不能根据保留通道的错误不断生成新候选，并继续把最终分数称为独立测试。

四通道均有历史开发曝光，且 CH3、CH31 同属相关录音块，因此这是开发性研究。扩大代码搜索空间并不会消除数据规模和独立性限制；跨录音泛化最终仍需要新增未参与设计的数据。

## 8. 第一版的工程组成与验收

以下为拟议接口职责，不表示已经实现：

1. **运行证据存档**：将完整开发运行与对应代码、skill、数据版本绑定。
2. **自主编程优化器**：具备代码和 trace 检索、诊断、编辑及基本检查能力，产出可执行候选。
3. **候选运行接口**：加载独立版本，并允许候选改变内部程序结构；具体函数签名待实现前确定。
4. **独立评估器**：从相同初态完整运行、强制预算、评分并保存 trace，不受候选修改。
5. **搜索记录与版本选择**：保存父子关系、修改依据、结果和接受决策，可回到既有版本。

第一版先验证一次完整的“开发运行完成 → 自主读取证据 → 自主修改代码 → 候选完整评估 → 接受或拒绝”循环。工程验收要求候选与结果可追溯、评估条件一致、旧版可保留、测试信息未进入搜索；不要求候选必须提高分数。

尚待确定：编程优化器及模型、候选运行接口、新依赖管理、每次会话预算、候选选择规则、重复次数，以及是否在第一版正式接入 GEPA 的候选管理和 ACE 的经验整理。以上选择不改变已经确定的开放式 harness 优化方向。
