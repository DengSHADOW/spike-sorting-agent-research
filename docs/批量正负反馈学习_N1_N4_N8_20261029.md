日期：2026-10-29。用户最初要求实现并测试三组配置，随后明确要求暂不跑实验，仅做代码验收。本文件记录新协议与预备运行入口，不预设实验结果。

## 本次改动

`OnlineLearner` 更新为 `replay-online-learning-v2-batched`。N 现在表示累计的有效专家反馈数，包括正确和错误回答；不再默认表示错题数。`sources=all` 同时接收真实编辑和推导 KEEP，来源、空理由均原样保留。

凑齐 N 条之后，将整批案例用于一次规则修改，而不是对 N 道题分别修改 N 次。当前严格重放的一个 round 可能有多道题：这些题先用同一 skill 完成作答，学习在 round 结束后执行，后续轮次才加载新 skill。N=1 不会在同一并行轮次中途切换策略。

当前 vLLM 服务最多接收 6 张图片，一道题最多 5 张。为支持 N=8，统一采用两步提议流程：

1. 每道反馈用原图、测量、原回答、专家动作与来源生成短证据记录，每个请求只包含一道题的图片。
2. 将 N 道题的证据、测量和反馈放在一起，让提议者综合提出最多 3 条 add/replace/remove 修改。

三组都使用同样流程。模型证据摘要不是专家理由，允许表达不确定性；不把原本没有理由的推导 KEEP 补写成人类解释。中间输入、图片哈希、证据摘要和提议全部保存。

整批都答对时，保留反馈计数与记录，结果标为 `all_correct_no_change`，不额外调用优化模型。混合批次中的正确题则作为修改依据和保护对象。N=1 下正确反馈通常落入此无修改分支；这正是批次构成影响学习方式的一部分，不应解释为每条正确反馈都必须生成新规则。

## 候选验收

静态检查继续固定 gate、contract 和输出 schema。只允许编辑规则；原实现已有 remove，本次不是新增“删除规则”能力。

对整批题分别用当前父 skill 和候选 skill 重答，接受条件为：

- 不把批内原来答对、或当前父 skill 能答对的题改错。
- 候选正确数严格高于当前父 skill 的重答正确数，也高于该批原始作答正确数。
- 再检查该批开始之前的最近 K=3 道已标注历史题，原来答对的不能改错。

不要求一次修好批内所有错误，否则 N 越大越难通过，比较会混入不等价的门槛。父 skill 也要重答，因为缓冲区中的答案可能由较早 skill 产生。单次重答仍不能消除随机波动，本实验不将一次接受视为统计显著的改善。

本次保持最近 K=3 的回归方式，没有加入跨 dataset 的长期案例池。每个 dataset 结束默认处理最后不足 N 条的反馈；未完成或停止的运行不做尾批学习。`--no-flush-online-feedback` 可关闭尾批处理，三组对照统一保持开启。反馈状态文件用于审计，不表示实现了完整运行续跑。

## 实验设置

延续昨天链式实验：Qwen3.5-27B，关闭 thinking，其他模型采样设置不变；从同一份原始 skill_v4 独立开始 N=1、4、8 三条链，不能把 N=1 的学习结果作为 N=4 的起点。

| 阶段 | 学习 | 冻结测试 |
|---|---|---|
| 基线 | 不学习 | CH31、CH3、CH30、CH20 |
| 1 | CH31 | CH3、CH30、CH20 |
| 2 | 接续上一阶段 skill 学 CH3 | CH30、CH20 |
| 3 | 接续上一阶段 skill 学 CH30 | CH20 |

CH20 始终不参与学习。本轮 CH30 是第三个学习通道；它在前两阶段只是尚未学习的前向测试，不是全程保留测试集。这与早期“CH3/CH31 学习、CH20/CH30 保留”的方案不同，采用的是用户本次要求延续的昨日链式设置。

默认先做每组一次，共 4 次基线加 27 次链式运行；`--repeats` 可增加整套重复，届时每条链重新从原始 skill 开始。三组统一并发 4、不开预取，以减少执行方式差异。历史重复测量保留，不把它们当作新协议的重复。

本次还改变了提议流程和验收方式，因此新 N=1 是三组比较的共同参照，不能把它与昨天“错题单独提议”的 N=1 当作只改变 N 的对照。它仍是内部批量修订方法，没有调用 GEPA 搜索引擎。

## 运行入口与防串版本

单通道参数：`--online-learning --feedback-batch-size 4 --online-feedback-scope all --feedback-sources all --regression-k 3`。

三组链式运行入口：`scripts/run/run_feedback_batch_sweep.py`。要求显式提供起始 skill，默认只打印计划；`--execute` 才调用模型。

```bash
/workspace/spike-sorting-agent/.venv/bin/python scripts/run/run_feedback_batch_sweep.py \
  --base-skill configs/controller_v2/skills/skill_v4.json \
  --output-root output/feedback_n_sweep_qwen27b_nothink_20261029 \
  --batch-sizes 1 4 8 --regression-k 3 --repeats 1 --execute
```

每次运行都导出 `final_skill.json`，包括没有接受修改的情况。链式脚本使用确切文件路径，并逐环检查 manifest 起始 skill 的版本/哈希、结果导出哈希、模型设置、N/K/反馈范围、完成状态以及测试阶段是否关闭学习；不再通过 shell 拼接猜测“最新 skill”。遇到失败立即停止，不跳过失败阶段继续学习。

远端环境以昨天实际运行的 `f1ca871` 为基底，使用独立目录 `/workspace/replay-feedback-nsweep-20261029`；不覆盖昨天的实验目录。仅叠加必要的重放与批量学习代码，模型、gate 和 skill_v4 保持远端基线版本。本地定制仓库的较早底座只用于开发与离线验证，不替换远端基线实现。

## 结果与时间报告

比较每通道总 accuracy、按动作/标签来源拆分的正确数，尤其关注 KEEP 与 DISCARD 的变化。学习轨迹分数与冻结测试分数分开，重放终态不作为 agent 成绩。

记录有效反馈总数、正确/错误反馈数、满批/尾批、接受/拒绝原因以及最终 skill。分开统计执行模型、逐题证据提炼、联合提议、批次验收与 K 题回归的调用和耗时。N 变大减少更新次数，但每批成本上升，不能预先承诺更快。

链式脚本持续生成 `summary.json`、`SUMMARY.md`；各运行保留完整 manifest、ledger、trace 和学习产物。只有全部完成才写 `completed.json`。本文件中的方案与离线测试不等于真实实验结果。
